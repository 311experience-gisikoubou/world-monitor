# L-0004: 同系統候補の解決介入が2回失敗したら、3回目の前に強制再考する

- ID: L-0004
- Title: アンチループ：2回失敗で強制再考・3回目前に根拠再構築
- Status: active
- Scope: common
- Approved: 2026-08-17

## Purpose（目的）

この「2回失敗したら3回目の前で止める」という閾値は、統計的に最適な失敗回数を主張するものではない。

目的は、同じ方向へ惰性で進み続ける前に、AI／人間の思考を強制的に1段上へ戻し、原因仮説・観測事実・解決経路を再構築するための**強制再考ポイント**を作ることにある。

3回目そのものを一律禁止するのではなく、2回失敗した時点で通常の試行モードを終了し、新しい根拠がある場合だけ3回目の解決介入を許可する。

## Count Target（何を数えるか）

カウントするのは、問題を解決するために結果を変えようとした**解決介入**だけとする。

例：

- コード・設定・構成・権限・経路を変更する
- 同じ解決経路を再実行して成功を狙う
- サービス・ライブラリ・ツール・接続方式を切り替える
- 人間へ設定変更・再接続・再入力・再試行などの操作を依頼する

次のような観測・調査は、原則として失敗回数へ含めない。

- ログ・状態・設定・コードを読む
- 安全なread-only診断を行う
- 既存情報を比較する
- 原因切り分けのための再現確認を行う
- 独立レビューを行う

ただし、名目が「確認」でも実際には状態を変え、成功を狙う介入であればカウント対象とする。

## Same-Loop Candidate（同系統候補）

以下のいずれかが実質的に同じなら「同系統候補」とする。完全一致は必要ない。

- 原因についての仮説・仮説カテゴリが同じ
- 同じ通信経路・外部サービス・ライブラリ・ツール・設定方式・実機操作で同じ目的を達成しようとしている
- 人間側へ同じ種類の確認・設定変更・再試行を繰り返させている
- 変更対象やコマンド表現だけを小さく変えているが、解決原理が同じ

変更対象ファイル集合の重なりは補助シグナルとして扱うが、それだけで別系統／同系統を決めない。

AI、セッション、コマンド表記、UI経路、言い換えが変わっても、原因仮説・解決原理・人間操作が実質同じなら同じループとして扱う。

## Early Interaction Signals（会話・操作上の早期兆候）

失敗回数だけを待たない。次のような同一文脈の再発は、解決介入の3回目より前に異常候補として扱う。

- 人間から同じ訂正（「違う」「それじゃない」「前に決めたやつ」等）が続く
- approved reference / 過去成果物を見失って同じ代替を出し直す
- 既に分かっている情報を人間へ再質問する
- 同じstatus確認やtimeout確認を繰り返す
- 作業は動いているが、保存されたCurrent Goalへ直接または補助的にも近づいていない

ローカルrepository経路がある場合、`stagnation-watch.mjs`の `--interaction-signal` / `--interaction-key` と `--goal-alignment` を使う。強い兆候である user-correction / reference-miss / reasked-known は1回目から `SUSPICIOUS` とし、同じ代替を出し直す前にHuman Decision Syncの現行決定とproject working memoryのApproved Reference / Current Goalを再読込する。同じinteractionの2回目は再試行前診断を要求し、3回目は `STOP_AND_DIAGNOSE` として同経路の惰性継続を止める。3回は許容回数ではなく最大目安であり、明確な兆候があればより早く原因分析へ移る。

## Forced Reflection Trigger（強制再考の発動）

同系統候補の解決介入が2回失敗した時点で、通常の解決試行を終了する。

3回目の解決介入へ進む前に、必ず次を整理して外部化する。

1. 失敗した2件の解決介入
2. 各介入で観測された結果
3. 現在の原因仮説の状態：`否定` / `弱まった` / `未確定`
4. 3回目を正当化する新しい根拠：`新しい観測` / `新しい仮説` / `別経路` / `実質的な条件変更`
5. 次に行うこと

十分な新しい根拠がない場合は3回目へ進まず、観測・原因分析へ戻る。

## Third Attempt Rule（3回目の扱い）

2回失敗後の「同じ方法をもう一度」は禁止する。名称・引数・表現だけを変えた実質同じ再試行も同じ扱いとする。

一方、強制再考の結果として、原因仮説・観測事実・解決経路・前提条件のいずれかが**技術的に実質変更された根拠**を示せる場合は、3回目の解決介入を1回だけ許可してよい。

これは履歴のリセットではない。過去2回の失敗記録は保持し、新しい根拠を得たことで一時的に再試行を許可する `half-open` 相当の扱いとする。

その3回目も失敗した場合は、同じ根拠のまま追加試行せず、再び観測・原因分析・別仮説・別経路・独立レビューへ戻る。

## Reflection Paths（強制再考で選べる経路）

2回失敗後は、少なくとも次のいずれかへ移る。

1. `root-cause-analysis`：観測を増やし、原因仮説を検証し直す
2. `hypothesis-reselection`：別の原因仮説へ切り替える
3. `route-reselection`：別方式・別経路を比較する
4. `independent-review`：L-0005の独立レビューを使う
5. `stop`：安全上または証拠不足により停止する

新しいソフト・サービスは「今の方法が失敗したから」という理由だけで採用しない。既存手段・OS標準・既契約機能と比較し、security/privacy、追加費用、外部依存、データ経路、日常操作、保守・復旧・撤去負担を確認し、`Simplest Safe Design`を満たす場合だけ候補とする。

## Human Boundary（人間への戻し方）

STOPや強制再考を、非エンジニアの人間への技術丸投げに変換しない。

AIは先に、観測 → 根本原因分析 → 別仮説 → 別経路 → 独立レビューの順で技術的に解決可能な範囲を尽くす。

人間へ戻すのは、技術的に解けないからではなく、実機でしか判断できない主観確認、業務方針、費用、責任、データ取扱いなど**本当に人間の価値判断が必要な場合だけ**とする。

非エンジニアの人間を、複数の技術案を順番に試すテスターとして扱わない。
