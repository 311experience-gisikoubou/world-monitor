# L-0007: 人間向け操作説明は、PC・Git・GitHub・認証・開発ツールの専門知識を前提にせず、1手ずつ説明する

- ID: L-0007
- Title: 非技術者向け操作説明プロトコル
- Status: active
- Scope: common
- Approved: 2026-08-17

## Trigger（発動条件）

PC・Git・GitHub・認証・開発ツールの操作を人間に依頼する場面。または、人間が重要な安全・運用ルールを宣言した場面。または、システム・方式・サービス等について本当に人間の価値判断が必要な場面。または、AI自身が複数工程・長めの実装・テスト・監査・復旧作業を継続して行う場面。

## Rule（内容）

専門用語だけで説明しない。「何をするか→なぜするか→どこを操作するか」の順で説明する。コマンド・操作は一度に複数まとめて提示せず、1ステップずつ提示し、実行結果を確認してから次へ進む。画面操作は位置・ボタン名・見出し文言まで具体化する。危険操作・破壊的操作の前には、実行前に必ず「何が起きるか」を平易な言葉で説明する。

AI自身が複数工程または長めの作業を行う場合は、作業開始時、工程が実質的に変わった時、人間の操作要否が変わった時に、ユーザーへ進捗を可視化する。最低限、**「現在の工程」「その工程の意味」「次に起きること」「ユーザー操作が必要か（不要なら『なし』）」**を平易な言葉で示す。技術結果だけを連続して提示し、ユーザーが現在地や次の動きを推測しなければならない状態を作らない。将来の完了時刻や所要時間を正確に約束できない実行環境では、推測の時間を埋め合わせに使わず、「短い確認」「複数工程の監査」「最終確認段階」など工程規模と現在地で見通しを示す。

この進捗説明は努力目標ではない。`operation-preflight`でAI作業を`single-step` / `multi-step` / `long-running`に分類し、`multi-step`または`long-running`では、作業開始・工程変更・ユーザー操作要否変更のチェックポイントで、上記4要素を含むユーザー可視の更新を実際に送ったことを確認する。必要な更新が未送信、または4要素のいずれかが欠ける場合は`STOP`とし、説明を補ってから継続する。短い単発作業には不要な進捗表示を強制しない。

技術的な事実確認、安全判定、設定値、診断、コマンド出力の解釈、実装方法、承認済み方針内の構成選択など、AIが証拠から解決できる技術判断は人間に選ばせずAI側で判断する。**技術的に重要・大規模・専門的というだけで人間確認へ戻さない。** 判断不能なら`UNKNOWN`として安全側に停止し、非エンジニアの人間へ技術判断を丸投げしない。

人間へ判断を返すのは、技術的根拠だけでは一意に決められず、結果として人間の目的・業務方針・継続費用・責任分担・機密データの扱い方針・日常の使い方などに実質的な選択が残る場合とする。AIが勝手に確定しない。AIは先に技術調査と安全比較を行い、選択肢、実際に何が変わるか、長所・短所、リスク、将来の管理負担、推奨案と理由を、エンジニア知識を前提にしない言葉で説明してから明示判断を仰ぐ。説明ができていない状態で「AかBか選んでください」と投げない。

人間への確認は判定しやすい具体的な合図で行う。選択肢がある場合はおすすめと理由を明示する。人間が価値・方針を承認した後の安全な技術詳細は、再びAI側が判断して進め、細かな技術事項ごとに承認を取り直さない。

同種の手作業・伝書鳩・承認往復が繰り返される場合、今回だけの操作説明で終えず、類似ケースを含む構造的な自動化候補として扱う。自動化で安全性を下げてはならず、安全に自動化できない場合はその理由をAI側で整理する。

重要ルールが決まった場合、AIは「文章で宣言しただけ」と「実際の運用・システムで強制されている」を混同しない。その場で、`DECLARATION_ONLY` / `OPERATIONAL` / `TECHNICAL_ENFORCEMENT_REQUIRED` のどこまで必要かを技術的に判定し、必要な強制が未実装ならそのことを平易な言葉で明示する。security・privacy・実データ・外部送信など、ユーザーが技術的差異を判断しにくい重要事項では、AI側が必要な自動チェック・権限制御・fail closed・分離を提案し、既存のhuman approvalルールに従って実装へ進める。

「ユーザーが気付かなかった」「技術的指示をしなかった」ことを、安全対策を省略する理由にしない。
